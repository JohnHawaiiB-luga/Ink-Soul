## Introducción

Esta guía está diseñada para ayudarte en la elaboración del **Proyecto Final del Ciclo**. Es fundamental que tu proyecto implemente tecnologías relacionadas con los módulos de tu ciclo formativo:

- **ASIR (Administración de Sistemas Informáticos en Red)**: Enfoca tu proyecto en redes, bases de datos, aplicaciones web, administración de sistemas, etc.
- **DAM/DAW (Desarrollo de Aplicaciones Multiplataforma/Web)**: Desarrolla una aplicación o web donde utilices lenguajes de programación, lenguajes de marcas, conexión con bases de datos, etc.

> **💡 Consejo**: No tienes por qué limitarte a las herramientas vistas en clase. De hecho, sería muy interesante que explores software diferente y tecnologías novedosas que enriquezcan tu proyecto.

## Paso 1: Pensar Proyectos a Realizar

### 🎯 Consulta con tu Tutor/a

- **Presenta varias ideas** de proyectos posibles a tu tutor/a
- Si no tienes ideas claras, **solicita sugerencias** basadas en tus intereses y habilidades
- Aprovecha la experiencia de tu tutor/a para validar la viabilidad del proyecto

### 🔍 Busca Inspiración

#### Proyectos Existentes
- Busca **ejemplos de proyectos** ya realizados por otros estudiantes en Internet
- Analiza qué les funcionó bien y qué podrían haber mejorado
- Usa estos proyectos como **guía y referencia**, no para copiarlos

#### YouTube y Comunidades
- Explora canales de tecnología en YouTube
- Busca proyectos de aficionados a la tecnología
- Identifica **componentes pequeños** que puedas integrar en un producto mayor
- Participa en comunidades como GitHub, Stack Overflow, Reddit (r/programming, r/webdev)

#### Ideas de Proyectos Populares
- Aplicaciones web completas (e-commerce, portfolio, blog)
- Sistemas de gestión (inventario, clientes, proyectos)
- APIs RESTful con documentación
- Aplicaciones móviles multiplataforma
- Sistemas de monitorización y administración
- Automatización de tareas y scripts
- Integraciones con servicios de terceros

### ⚡ Introducción del Proyecto

La introducción debe ser clara y captar el interés del lector. Incluye:

#### 📝 Presentación del Tema
- ¿Qué es tu proyecto?
- ¿A qué ámbito o sector pertenece?
- Breve descripción general

#### 🎯 Relevancia
- ¿Por qué es importante este proyecto?
- ¿Qué problema real resuelve?
- ¿Quién se beneficiaría de tu solución?

#### 🎓 Contexto del Problema
- Describe la situación actual
- Explica las limitaciones o carencias existentes
- Justifica la necesidad de tu proyecto

#### ✅ Justificación
- ¿Por qué elegiste este tema?
- ¿Qué te motivó?
- ¿Cómo se relaciona con tu formación?

#### 🎯 Objetivos
Define objetivos claros y medibles:

**Objetivo General:**
- El resultado final que quieres alcanzar

**Objetivos Específicos:**
- Desglose de metas concretas (3-5 objetivos)
- Deben ser SMART (Específicos, Medibles, Alcanzables, Relevantes, Temporales)

**Ejemplo:**
```
Objetivo General:
Desarrollar una aplicación web completa para la gestión de citas y 
portfolio de un estudio de tatuaje.

Objetivos Específicos:
1. Implementar un sistema de reserva de citas con calendario visual
2. Crear una galería dinámica de trabajos con filtros por categoría
3. Integrar un sistema de pagos seguro con Stripe
4. Desarrollar un panel de administración con roles de usuario
5. Garantizar diseño responsive y accesible (WCAG 2.1 AA)
```

### 🗓️ Planificación

Una buena planificación es clave para el éxito del proyecto. Incluye:

#### 📅 Cronograma

Crea un diagrama temporal con las fases del proyecto:

**Herramientas recomendadas:**
- Diagrama de Gantt (Excel, Google Sheets, ProjectLibre)
- Trello / Notion / GitHub Projects
- Microsoft Project

**Fases típicas:**
1. **Investigación y análisis** (1-2 semanas)
2. **Diseño y planificación técnica** (1 semana)
3. **Implementación - Frontend** (3-4 semanas)
4. **Implementación - Backend** (2-3 semanas)
5. **Integración y testing** (1-2 semanas)
6. **Documentación y pulido** (1 semana)
7. **Preparación de la defensa** (1 semana)

#### 💰 Estimación de Costes

Realiza un análisis económico realista que incluya:

**1. Recursos Humanos:**
- Tu tiempo de trabajo (horas × tarifa por hora)
- Ejemplo: 200 horas × 15€/hora = 3.000€

**2. Recursos Materiales:**
- Hardware (ordenador, servidor, dispositivos de prueba)
- Licencias de software (si no usas alternativas gratuitas)

**3. Recursos Externos:**
- Hosting / Cloud services (Vercel, Netlify, AWS, etc.)
- Servicios de pago (Stripe, SendGrid, etc.)
- APIs de terceros
- Dominio web

**4. Otros Gastos:**
- Electricidad e Internet
- Material de oficina
- Formación complementaria

- Hosting: Vercel, Netlify, AWS, Heroku

- CI/CD: GitHub Actions, GitLab CI

**Diagramas recomendados:**

1. **Diagrama de Arquitectura General**

   - Flujo de comunicación entre componentes
   
2. **Diagrama de Base de Datos**

3. **Diagrama de Flujo**
   - Flujos de usuario principales

4. **Diagrama de Componentes** (para frontend)

#### 🛠️ Decisiones Técnicas

Documenta y justifica tus elecciones:

**Stack Tecnológico Final:**
- Frontend: ¿Por qué React y no Vue?
- Backend: ¿Por qué Supabase y no Firebase?
- Base de datos: ¿Por qué PostgreSQL y no MongoDB?

**Ejemplo:**
```
Frontend: React + TypeScript
Justificación: 
- Gran ecosistema y comunidad activa
- TypeScript para mayor seguridad de tipos
- Excelente rendimiento con Virtual DOM
- Amplia disponibilidad de librerías

Backend: Supabase (PostgreSQL + Edge Functions)
Justificación:
- Base de datos relacional robusta (PostgreSQL)
- Autenticación integrada
- Row Level Security para protección de datos
- Edge Functions con Deno (TypeScript nativo)
- Plan gratuito generoso

Estilos: Tailwind CSS
Justificación:
- Desarrollo rápido con utility-first
- Tamaño optimizado en producción
- Fácil personalización de design system
- Excelente documentación
```

#### ❗ Problemas Encontrados y Soluciones

Esta es una sección **MUY VALORADA** por el tribunal. Demuestra:
- Capacidad de resolución de problemas
- Pensamiento crítico
- Aprendizaje durante el desarrollo

**Formato recomendado:**

```
Problema 1: CORS al conectar frontend con backend
Descripción: Al hacer peticiones desde localhost:5173 a la API 
en localhost:3000, recibía errores CORS.

Solución: Configuré el middleware CORS en Express permitiendo 
el origen del frontend en desarrollo. En producción, configuré 
la lista de orígenes permitidos como variable de entorno.

Código:
```javascript
app.use(cors({
  origin: process.env.ALLOWED_ORIGINS.split(','),
  credentials: true
}));
```
```

### 📊 Diapositivas

#### 🎨 Diseño de la Presentación

**Principios básicos:**
- **Menos es más**: Evita saturar las diapositivas con texto
- **Visual storytelling**: Usa imágenes, diagramas y gráficos
- **Consistencia**: Mantén el mismo estilo en todas las diapositivas
- **Legibilidad**: Fuentes grandes (mínimo 24pt para texto, 32pt para títulos)

**Estructura sugerida:**
```
1. Portada (nombre, autor, fecha)
2. Índice (agenda de la presentación)
3. Introducción (contexto y motivación)
4. Objetivos (qué querías lograr)
5. Investigación (estado del arte, competidores)
6. Diseño (mockups, arquitectura)
7. Tecnologías (stack elegido)
8. Implementación (funcionalidades clave)
9. Demo (mostrar el producto funcionando)
10. Pruebas (resultados de testing)
11. Problemas y soluciones (desafíos superados)
12. Conclusiones (aprendizajes y reflexión)
13. Mejoras futuras (roadmap)
14. Bibliografía
15. ¿Preguntas?
```

#### 🚫 Qué Evitar

- ❌ Párrafos largos de texto
- ❌ Leer literalmente de las diapositivas
- ❌ Animaciones excesivas o distractoras
- ❌ Fuentes muy pequeñas
- ❌ Fondos que dificulten la lectura
- ❌ Demasiadas diapositivas (máximo 15-20)

#### ✅ Qué Incluir

- ✅ Puntos clave (bullets) breves
- ✅ Capturas de pantalla de tu proyecto
- ✅ Diagramas y esquemas visuales
- ✅ Código solo si es absolutamente necesario (y poco)
- ✅ Gráficos de resultados de pruebas
- ✅ Comparativas visuales (antes/después, tu proyecto vs. otros)

**Herramientas recomendadas:**
- Google Slides (colaborativo, gratis)
- PowerPoint / Keynote (clásicos)
- Canva (diseños profesionales)
- Reveal.js (presentaciones en HTML)
- Prezi (presentaciones no lineales)

### 👩‍🏫 Exposición Oral

#### 🎯 Preparación

**Practica, practica, practica:**
- Ensaya tu presentación **al menos 3-5 veces**
- Hazlo frente a familiares o amigos para recibir feedback
- Grábate en vídeo para identificar muletillas y gestos
- Practica con un cronómetro para ajustar el tiempo

**Prepara notas (no guiones):**
- Ten puntos clave escritos, no todo el texto
- Usa tarjetas o notas del presentador en las diapositivas
- No memorices palabra por palabra (sonará antinatural)

#### 🗣️ Durante la Presentación

**Lenguaje corporal:**
- Mantén contacto visual con el tribunal
- Usa gestos naturales para enfatizar puntos importantes
- Si tienes las manos inquietas, sostén algo (bolígrafo, puntero)
- Mantén una postura erguida pero relajada

**Voz y dicción:**
- Habla a un ritmo moderado (ni muy rápido ni muy lento)
- Haz pausas estratégicas para dar énfasis
- Varía el tono para mantener el interés
- Proyecta la voz con confianza

**Manejo de nervios:**
- Respira profundamente antes de empezar
- Recuerda que el tribunal **quiere que te vaya bien**
- Un poco de nerviosismo es normal y hasta positivo
- Ten agua cerca por si se te seca la garganta

#### ❓ Preguntas del Tribunal

**Anticipa preguntas:**
- "¿Por qué elegiste esta tecnología y no otra?"
- "¿Cómo manejas la seguridad de los datos?"
- "¿Qué harías diferente si empezaras de nuevo?"
- "¿Cómo escalaría tu proyecto para más usuarios?"
- "¿Cuál fue el mayor desafío técnico?"

**Responde con confianza:**
- Si sabes la respuesta, explícala con claridad
- Si no sabes, sé honesto: "No lo he implementado, pero creo que podría hacerse con..."
- Relaciona las respuestas con lo que SÍ hiciste en tu proyecto
- Nadie espera que lo sepas todo, pero sí que conozcas TU proyecto

**Estructura de respuesta:**
```
1. Comprende la pregunta (repítela si es necesario)
2. Da una respuesta directa
3. Proporciona contexto o justificación
4. Relaciona con tu proyecto si es posible

Ejemplo:
Pregunta: "¿Por qué usaste PostgreSQL en lugar de MongoDB?"

Respuesta: "Elegí PostgreSQL porque mi proyecto requiere 
relaciones complejas entre entidades: usuarios, productos, 
órdenes y citas. PostgreSQL ofrece integridad referencial 
y transacciones ACID, que son críticas para un sistema de 
pagos. Además, Supabase, que uso como backend, está construido 
sobre PostgreSQL y ofrece Row Level Security nativo."
```

### 📺 Demostración en Directo

Una demostración en vivo es **MUY efectiva** para impresionar al tribunal.

#### ✅ Preparación de la Demo

**Antes del día:**
1. **Prueba todo** exhaustivamente en el equipo que vas a usar
2. Verifica la conexión a Internet
3. Prepara cuentas de prueba con datos de ejemplo
4. Ten URLs y credenciales a mano
5. Cierra aplicaciones innecesarias
6. Desactiva notificaciones
7. Limpia el escritorio
8. Usa modo incógnito o perfil limpio del navegador

**Workflow de la demo:**
- Planifica un **flujo lógico** de 3-5 minutos
- Muestra las funcionalidades más importantes
- Empieza por lo más impactante visualmente
- Termina con algo memorable

**Ejemplo de flujo:**
```
1. Página de inicio (diseño, hero)
2. Navegación por el portfolio (filtros, lightbox)
3. Formulario de cita (calendario, validación)
4. Tienda (productos, carrito, checkout con Stripe test)
5. Responsive (redimensionar ventana o mostrar en móvil)
6. Panel admin (si aplica)
```

#### 🎥 Plan B: Vídeo de Backup

**SIEMPRE ten un vídeo grabado** por si falla algo:
- Internet se cae
- Servidor no responde
- Error inesperado en el código
- Problemas técnicos del aula

**Cómo grabar un buen vídeo:**
- Usa OBS Studio (gratis) o similar
- Graba en HD (1080p mínimo)
- Incluye audio explicando lo que haces
- Edita para que dure 3-5 minutos máximo
- Prueba el vídeo en varios reproductores
- Llévalo en USB y también en la nube (Google Drive)

#### 💡 Consejos para la Demo

**Durante la demostración:**
- **Narra lo que haces**: "Ahora voy a crear una cita nueva..."
- Usa **datos de ejemplo realistas** (no "test test test")
- Si algo falla, mantén la calma y pasa al vídeo backup
- **No te disculpes** por pequeños detalles visuales
- Destaca características técnicas complejas

**Señala aspectos técnicos:**
- "Como ven, valido en tiempo real el email"
- "Aquí uso debouncing para no saturar la API"
- "Las imágenes están optimizadas con lazy loading"
- "Este modal tiene accesibilidad con navegación por teclado"

### ⏳ Gestión del Tiempo

El tiempo es limitado. Respétalo y úsalo estratégicamente.

#### ⏰ Tiempo Típico

La mayoría de defensas son de **15-30 minutos**:
- 10-20 minutos de presentación
- 5-10 minutos de preguntas

**Confirma el tiempo exacto** con tu tutor/a.

#### 📏 Distribución del Tiempo

**Para una presentación de 15 minutos:**
```
0:00 - 1:00   Introducción y contexto
1:00 - 2:00   Objetivos del proyecto
2:00 - 3:00   Investigación y tecnologías
3:00 - 4:00   Diseño y arquitectura
4:00 - 6:00   Implementación (funcionalidades clave)
6:00 - 10:00  DEMO en vivo ⭐
10:00 - 12:00 Pruebas y resultados
12:00 - 14:00 Problemas, conclusiones y mejoras futuras
14:00 - 15:00 Cierre y transición a preguntas
```

**Para una presentación de 25 minutos:**
- Puedes profundizar más en cada sección
- Dedica más tiempo a la demo (7-8 minutos)
- Muestra más detalles técnicos

#### ⏱️ Práctica con Cronómetro

**Durante los ensayos:**
1. Usa un cronómetro visible
2. Anota el tiempo de cada sección
3. Identifica dónde te extiendes demasiado
4. Ajusta el contenido para cumplir el tiempo
5. Deja margen de 1-2 minutos por imprevistos

**Estrategias si te quedas sin tiempo:**
- Ten identificado qué puedes saltar
- Diapositivas "opcionales" que puedes omitir
- Acelera en las secciones menos críticas
- La demo y las conclusiones son sagradas

**Estrategias si sobra tiempo:**
- Ten contenido extra preparado (opcional)
- Profundiza en algo que despertó interés
- Menciona más mejoras futuras
- Invita a preguntas antes de tiempo

## 🎯 Consejos Finales

### 💎 Oro

- **Empieza pronto**: No dejes todo para el último mes
- **Documenta desde el día 1**: Es mucho más difícil recordar después
- **Comunica con tu tutor/a**: Reuniones regulares previenen problemas
- **Haz commits frecuentes** en Git: Tu historial cuenta una historia
- **Testea constantemente**: No acumules bugs para el final

### 🌟 Plata

- **No te compares**: Cada proyecto es único
- **Aprende del feedback**: Cada crítica es una oportunidad
- **Backup, backup, backup**: Murphy's Law es real
- **Cuida tu salud**: Descansa, come bien, haz ejercicio
- **Disfruta el proceso**: Estás aprendiendo y creando algo propio

### 🥉 Bronce

- **Sé auténtico**: Muestra tu personalidad en el proyecto
- **Pide ayuda**: Nadie espera que lo hagas solo
- **Celebra los pequeños logros**: Cada feature completado cuenta
- **Mantén scope razonable**: Mejor un proyecto pequeño pulido que uno grande a medias
- **Confía en ti**: Has llegado hasta aquí, puedes con esto
